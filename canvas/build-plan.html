Part 2 · the target

How an action gets recorded, and how one gets taken

One rule replaces the whole sheet: every action is a row in one table. The pipeline writes them, the outside world writes them, and a person clicking a button writes them. A lead's status is never edited — it is read off the latest row. The interface is a view of that table. n8n reacts to new rows instead of polling.

A lead's status is derived from its newest event. "Where is this lead?" and "who did what?" are the same question with the same answer.
Part 3 · the work

Four phases, in the order they can actually happen

Numbered because each depends on the one before. Phase 0 runs on today's infrastructure so the loop is closed before anything moves. Phase 1 gives Phase 2 something to be built on.

0
Close the loopthis weekon the current sheet — nothing moves yet

The send path works. What is missing is everything after a prospect says yes. None of this waits for a database.

  1. 0.1Copy. Lead with the offer, name Gavriel as who they will meet ("fifteen minutes with Gavriel, who runs OryonIQ"), keep Ellen as the sender. Re-sync to Instantly, the page, and both agents.
  2. 0.2Reply automation. Positive → Ellen replies in-thread with the HubSpot link, Slack gets the thread with context. Negative → suppressed. Out-of-office → parked with a date. Every branch writes an event.
  3. 0.3Booking webhook. HubSpot "meeting created" → lead marked meeting_booked, sequence stopped, Slack told. This is the conversion event and the number the boss will ask for.
  4. 0.4Boss's spreadsheet. One-off import into Inbox. The alias table already reads any column shape; his rows go through the same verify → draft → send path as everything else.
0.3 is blocked on HubSpot access — see Part 5.
done whenA test reply produces the right action with nobody touching it, and a test booking stops the sequence and lands in Slack.
1
One databasenextSupabase becomes the record; the sheet retires

This is the phase that removes the root cause of most of Part 1. A real schema, real transactions, and triggers that fire on a new row instead of a clock.

  1. 1.1New Supabase project — separate from IndustrialBriefs'. Tables: leads, events, suppression, replies, campaigns, staff. Suppression stays append-only and matches on any identifier, exactly as now.
  2. 1.2Migrate the current Leads, Events and Suppression tabs. Every historical send becomes an event row.
  3. 1.3Repoint n8n. Sheets nodes → Postgres nodes, one workflow at a time, each verified from its execution snapshot before the next. A database webhook on leads insert replaces the 2-minute poller.
  4. 1.4Sheet as mirror for one week, read-only, then off. Instantly's own events (open, bounce, reply) sync in so the database knows everything Instantly knows.
done whenA lead inserted into the table is verified, drafted, and sent with no poller involved, and every step of that is a row in events.
2
One screenthenthe interface, on the DigitalOcean droplet

Everything the boss and staff currently need Instantly, the sheet, and Slack for, in one place they can read. Every button writes an event, so a click is a record.

  1. 2.1Logins. Supabase Auth. Boss and staff each have a name, so "who approved this" has an answer.
  2. 2.2Leads board. Status, product, source, last action. Filter and search. Open a lead: the full timeline from events — verified, drafted, sent, opened, replied, booked.
  3. 2.3Add and upload. Type one lead, or drop a CSV or Excel. Goes into staging, then the same intake path. Bad rows are shown with the reason, and fixing one re-submits it.
  4. 2.4Reply inbox. Read the reply, see the sentiment, one click to book, park, or suppress. No Instantly login.
  5. 2.5Dashboard. Sent, opened, replied, booked — today and this week. Sending-account health. Suppression count. The screen the boss opens.
done whenNobody on the team opens Instantly or the sheet for a full working day.
3
Volumeaftersupply, then scale

Only now does it make sense to turn the tap on. The path is proven, the record is real, and a person can see what is happening.

  1. 3.1Apollo → the same intake. Sourced leads land in the same table with source = apollo and pass the same verification and suppression checks as a typed one. The workflows exist; this is wiring.
  2. 3.2Raise the cap toward 100 a day, watching bounce rate and warmup scores in the dashboard. Add sending accounts before raising, never after.
  3. 3.3Ask the data. The agent already exists. Pointed at this table, "show me everyone who replied this week and hasn't booked" becomes a sentence, not a filter.
done whenA week runs at target volume with no one typing a lead and no one asking where a lead went.
Part 4 · settled

Decisions already made

OryonIQ markets alone

No parent-company mention anywhere a prospect reads. Sender, signature, postal line and page are done and live.

Ellen sends, Gavriel meets

Outreach stays under the Ellen persona; the calendar and the meeting are Gavriel's. The copy names him, so the handoff reads as an SDR booking for the founder — normal, not jarring.

Four accounts, not new ones

Rotation across the four warmed @getoryoniq.com mailboxes. No new domains, no warmup wait, 120/day capacity.

Supabase, new project

Separate from IndustrialBriefs'. Postgres, auth, and database webhooks in one place n8n already speaks to.

DigitalOcean hosting

The interface lives on the existing droplet. One place to look, no new vendor.

Nothing deleted

All twenty workflows stay; the Apollo leg is the supply for Phase 3. Note that the live sender's id still reads VIOwfDsheetdemo1 — it is not a demo.

Part 5 · needed from you

Two things unblock everything above

HubSpot access

A private-app token, or Super Admin on the account. Without it the pipeline cannot see a booking — a booked prospect keeps getting follow-ups and the conversion is never counted. Blocks 0.3.

Supabase authorisation

Authorise the Supabase connector in claude.ai settings, or create the project and put its URL and service key in .secrets.env. Blocks Phase 1.
